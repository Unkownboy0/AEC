## Mentor Attendance Risk / Academic Risk metrics — implemented properly (not hardcoded)

Previously both cards always showed 0 (no backend field existed at all). Implemented in [mentor.service.ts:getDashboardStats](product/server/src/modules/mentor/mentor.service.ts):

- Added two configurable `SystemSetting` entries to the catalog ([settings.catalog.ts](product/server/src/modules/settings/settings.catalog.ts)): `ATTENDANCE_RISK_THRESHOLD` (already existed but was unused anywhere in the codebase — default 75%) and new `ACADEMIC_RISK_ARREAR_THRESHOLD` (default 1 — number of published grade-F marks that flags a student).
- `attendanceRiskCount`: per mentee, `prisma.attendance.groupBy` computes all-time present/total, flags if `< attendanceRiskThreshold` (only when the student has at least one attendance record — a mentee with zero attendance history is not counted as "at risk" by omission).
- `academicRiskCount`: per mentee, `prisma.mark.groupBy` counts `PUBLISHED` marks with `grade: 'F'`, flags if `>= arrearRiskThreshold`.
- Both thresholds are echoed back in the response (`attendanceRiskThreshold`, `arrearRiskThreshold`) so the frontend can display the policy, not just the count.
- Added `riskStudents` array (id/admissionNo/name of every mentee flagged by either metric) — replaces the previous permanent "No Mentees at Risk" empty state.
- Frontend ([MentorDashboardPage.tsx:77-78](product/client/src/modules/mentor/pages/MentorDashboardPage.tsx:77)) updated to read `data.metrics.attendanceRiskCount`/`academicRiskCount` instead of nonexistent flat fields.

**Verified live end-to-end**: API returns `attendanceRiskCount: 2, academicRiskCount: 0` for `mentor1.cse@geetorus.com` (real computed values, cross-checked against Suresh Kumar's own student dashboard which independently showed 4.55% attendance). Actual UI reload shows "ATTENDANCE RISK: 2" and lists "CSE Student 002" and "Suresh Kumar" under "High-Risk Mentees", replacing the fake-empty state.

**Cosmetic gap — now fixed.** `mentor.service.ts`'s `riskStudents` mapping now includes `attendancePercent`, `arrearCount`, `isAttendanceRisk`, `isAcademicRisk`, and a human-readable `reason` string per flagged student (e.g. "Attendance 4.5% is below the 75% threshold"), built from the same per-student risk-detection loop that computes the aggregate counts — not a separate/duplicated calculation. Frontend field names corrected to match (`admissionNo`/`attendancePercent`/`arrearCount`, with fallback to the old `rollNo`/`attendancePercentage`/`arrearsCount` names in case anything else reads this payload). **Verified live in the actual UI**: "CSE Student 002 (ADM-CSE-2026-002) — Attendance: 0% • Arrears: 0 — Attendance 0% is below the 75% threshold" and "Suresh Kumar (ADM-CSE-2026-001) — Attendance: 4.5% — Attendance 4.5% is below the 75% threshold" (4.5% independently cross-checked against Suresh Kumar's own student-facing dashboard).

## Root-caused AND fixed this session

**HOD dashboard blank/zero stats — FIXED.** Traced via live network capture: the page calls `GET /api/hod/dashboard`, handled by `hod.controller.ts#getDashboardSummary`. The API was already returning correct data (`activeFaculty: 13, totalFaculty: 13, totalStudents: 1` — confirmed via direct fetch), but as a **flat** object (`{ success, data: { totalFaculty, ... } }`). The frontend ([HodDashboardWorkspace.tsx:44-45](product/client/src/pages/hod/HodDashboardWorkspace.tsx:44)) reads `data.summaryCards` and `data.department` — neither existed in the response, so both silently defaulted to `{}`, producing the observed "Assigned department (—)" / all-zero cards. Fixed by reshaping the controller's response to `{ summaryCards: <the existing metrics object>, department: { id, name, code } (sourced from the already-correct req.hodContext), widgets: { recentRequests } }` — no change to the service/repository layer, which was already correct. **Verified live end-to-end**: re-fetched the API (correct nested shape confirmed) and reloaded the actual HOD dashboard UI — now shows "Computer Science & Engineering (CSE)", "ACTIVE DEPARTMENT FACULTY: 13", "TOTAL DEPARTMENT STUDENTS: 1".

**Mentor workspace "Assigned Mentees: 0" — FIXED.** Same class of bug: `GET /api/mentor/dashboard` already returned correct data (`metrics.totalAssignedStudents: 20`), but [MentorDashboardPage.tsx:73-76](product/client/src/modules/mentor/pages/MentorDashboardPage.tsx:73) read flat top-level fields (`data?.assignedStudents`, `data?.presentToday`, `data?.absentToday`, `data?.pendingLeaveCount`) that don't exist in the actual response shape (`{ mentorInfo, metrics: {...}, recentStudents }`). Fixed by reading `data?.metrics?.totalAssignedStudents` etc. first, with the old flat-field reads kept as a fallback (harmless, costs nothing, guards against any other caller shape). Verified live: mentor workspace now shows "ASSIGNED MENTEES: 20", "PENDING LEAVE & OD: 1", matching the API payload.

Note: `criticalAttendanceCount`/`academicRiskCount` on this same page ([MentorDashboardPage.tsx:77-78](product/client/src/modules/mentor/pages/MentorDashboardPage.tsx:77)) have no corresponding field anywhere in the `/api/mentor/dashboard` response at all — not a mapping bug, a genuinely missing backend metric. "ATTENDANCE RISK" and "ACADEMIC RISK CASES" cards will always show 0 until the backend computes and returns these. Flagged, not fixed (would require backend work to define the risk thresholds and query).

Also noted in passing (not a bug): mentor's `recentStudents` correctly show `departmentName: "Science & Humanities"` for CSE-admitted first-year students — this is the S&H year-1 academic-operating-unit design working as intended (spec section 13/18), a positive finding.

## Verdict so far

**NOT READY FOR PRODUCTION**, but materially more secure than session start.
